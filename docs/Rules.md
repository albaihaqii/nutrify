# Development Rules

| Field        | Value                                                                   |
| ------------ | ----------------------------------------------------------------------- |
| Product      | Nutrify                                                                 |
| Version      | 0.1 (draft)                                                             |
| Audience     | Everyone who writes code or docs in this repository                     |
| Last updated | 2026-11-05                                                              |
| Related      | [Architecture](Architecture.md), [Schema](Schema.md), [Setup](Setup.md) |

These rules keep the repository consistent. When a rule and a habit disagree, the rule wins.
When a rule is wrong, change the rule in a pull request instead of ignoring it.

## 1. Language

| Area                                          | Language                      |
| --------------------------------------------- | ----------------------------- |
| Folder names, file names, code, identifiers   | English                       |
| Code comments, docstrings, commit messages    | English                       |
| Documentation in `docs/`                      | English                       |
| API field names, enum codes, database columns | English                       |
| Text shown to end users in the web app        | Indonesian (Bahasa Indonesia) |

Rules for user-facing text:

- All Indonesian text lives in `frontend/src/locales/id.ts`. Components reference keys, never
  hard-coded strings.
- The backend returns codes (`n_deficiency`, `sensor_out_of_range`), never Indonesian sentences.
  The frontend maps codes to labels.
- Exception: advice text generated by the advisor is Indonesian because the end user reads it
  directly. The advisor prompt requests Indonesian output; the JSON keys stay English.

## 2. Naming

| Item                                 | Style                    | Example                          |
| ------------------------------------ | ------------------------ | -------------------------------- |
| Python modules, functions, variables | `snake_case`             | `compute_leaf_area`              |
| Python classes                       | `PascalCase`             | `SensorReading`                  |
| Python constants                     | `UPPER_SNAKE_CASE`       | `DEFAULT_PH_MIN`                 |
| Database tables                      | plural `snake_case`      | `sensor_readings`                |
| Database columns                     | `snake_case`             | `recorded_at`                    |
| TypeScript variables, functions      | `camelCase`              | `fetchLatestReading`             |
| React components, TypeScript types   | `PascalCase`             | `PlantCard`, `SensorReading`     |
| Frontend files and folders           | `kebab-case`             | `plant-card.tsx`, `live-camera/` |
| API paths                            | lowercase, plural nouns  | `/api/sensor-readings`           |
| JSON fields                          | `snake_case`             | `recorded_at`                    |
| Environment variables                | `UPPER_SNAKE_CASE`       | `DATABASE_URL`                   |
| Git branches                         | `type/short-description` | `feat/live-camera`               |

General naming rules:

- Names describe purpose, not type or history (`stable_class`, not `result2`).
- Units go in the name when not obvious (`analysis_interval_seconds`).
- No abbreviations except the standard domain terms: `ph`, `ec`, `tds`, `roi`, `hsv`, `rgb`.
- Boolean names read as questions: `is_active`, `has_snapshot`.

## 3. Repository structure

- Each top-level folder has one responsibility: `frontend/`, `backend/`, `ml/`, `firmware/`,
  `scripts/`, `docs/`, `storage/`.
- Code never imports across top-level folders. The backend reads trained models from
  `ml/models/` through files, not by importing notebook code.
- Shared constants (class codes, feature order) are defined once in the backend and in
  `ml/models/registry.json`; other places read them, they do not redefine them.
- Generated and runtime files (`storage/`, `ml/data/raw`, `ml/data/interim`, `.venv`,
  `node_modules`) are never committed.
- Every new folder that must exist while empty contains a `.gitkeep`.

## 4. Git workflow

### 4.1 Branches

- `main` is always working and always deployable. It is the only long-lived branch.
- Work happens on short-lived branches named `type/short-description`, where `type` is one of
  the commit types below.
- Merge to `main` through a pull request, even when working alone, so history stays reviewable
  and CI runs. Prefer squash merge to keep one commit per change.
- Delete branches after merging.

### 4.2 Commit messages (Conventional Commits)

Format:

```
<type>(<scope>): <summary in imperative mood>

<optional body: what and why>
```

| Type       | Use for                                                 |
| ---------- | ------------------------------------------------------- |
| `feat`     | A new feature                                           |
| `fix`      | A bug fix                                               |
| `docs`     | Documentation only                                      |
| `refactor` | Code change that neither fixes a bug nor adds a feature |
| `test`     | Adding or changing tests                                |
| `chore`    | Tooling, dependencies, configuration                    |
| `style`    | Formatting only, no logic change                        |
| `perf`     | Performance improvement                                 |
| `ci`       | CI configuration                                        |

Scopes: `frontend`, `backend`, `ml`, `firmware`, `docs`, `db`, `worker`, `api`, `scripts`.

Rules:

- Summary in English, imperative mood, lowercase, no trailing period, at most 72 characters.
- One logical change per commit. Do not mix a refactor with a feature.
- Never commit secrets, large raw datasets, or generated files.

Examples:

```
feat(backend): add sensor ingestion endpoint
fix(worker): release webcam on shutdown
docs: add database schema
chore(frontend): remove unused template pages
```

### 4.3 Pull requests

A pull request description states what changed, why, and how it was tested. It links the
requirement (`FR-xx`) when one applies. A pull request is ready when the checklist in section 11
is satisfied.

## 5. Python code (backend, worker, ml)

- Python 3.10, one shared root `.venv`.
- Formatter and linter: `ruff` (`ruff format`, `ruff check`). Line length 100.
- Type hints on all public functions and on every function in `services/`.
- Layering in the backend: routes parse and validate input, call a service, and return the
  response. Business logic lives in `services/`. Database access lives in services or model
  helpers, never in routes.
- Validate all request bodies with Pydantic schemas in `app/schemas/`.
- No bare `except:`. Catch specific exceptions and log them.
- Use `logging`, not `print`, outside notebooks and one-off scripts.
- Configuration comes from `app/config.py`, which reads environment variables. No hard-coded
  paths, URLs, or credentials.
- Functions stay small and single-purpose. Image processing steps are separate functions so
  each can be tested and visualised on its own.

## 6. TypeScript and React code (frontend)

- Strict TypeScript. No `any` unless commented with the reason.
- Formatter and linter: the ones configured by the template (Prettier, ESLint). Run them before
  committing.
- Folder layout follows features: `features/<name>/` holds that feature's components, hooks,
  and API calls. Generic UI lives in `components/`.
- Server data goes through TanStack Query. Zustand holds only client state (session, UI
  preferences). Do not copy server data into Zustand.
- API calls live in one place per feature, use the shared Axios instance, and have typed
  responses in `types/`.
- Components are small and presentational where possible; data fetching stays in hooks.
- Every page handles four states: loading, empty, error, and success.
- Accessibility basics: labels on form fields, visible focus, sufficient contrast, keyboard
  navigation for interactive elements.

## 7. API rules

Details are in [API](API.md). The non-negotiable parts:

- All endpoints live under `/api` and return JSON.
- Errors use one shape: `{ "error": { "code": "...", "message": "..." } }`, with the correct
  HTTP status. `code` is a stable English identifier.
- Browser clients authenticate with a JWT bearer token. Devices authenticate with `X-API-Key`.
- Timestamps are ISO 8601 in UTC (`2026-11-05T02:40:00.000Z`). Only the frontend converts to
  Asia/Jakarta for display.
- Changing a response shape is a breaking change and requires updating [API](API.md) in the
  same pull request.

## 8. Database rules

- Schema changes go through migrations (`flask db migrate`, then review, then `flask db upgrade`).
  Never edit the database by hand and never edit a migration that is already on `main`.
- Always read the generated migration before committing it. Auto-generation can miss renames
  and enum changes.
- Every migration has a working downgrade, or a comment explaining why it cannot.
- Follow [Schema](Schema.md). If a change is needed, update the schema document in the same
  pull request.
- Store timestamps in UTC. Store units as defined in the schema.

## 9. Machine learning rules

- Evaluate models with the same split and the same metrics so they are comparable.
- Split by plant and time block, never by random row, so near-identical frames cannot leak
  between train and test.
- Fit scalers and any preprocessing on the training set only.
- Fix random seeds and record them with every result.
- Every trained model is registered in `ml/models/registry.json` with version, date, feature
  order, class order, dataset description, and metrics.
- The feature order is part of the model. The runtime classifier reads it from the registry
  and fails loudly on a mismatch.
- Data collected for the dataset uses the runtime webcam with locked exposure and white
  balance. Synthetic or assignment data is never reported as real performance.
- Report limitations honestly (class imbalance, small N-deficiency sample, single location).
- Notebooks are for exploration. Reusable logic moves to `ml/src/` as functions; notebooks
  import it. Notebooks are committed with outputs cleared, except those intentionally saved
  as reports in `ml/reports/`.

## 10. Security and secrets

- Secrets live only in `.env` files, which are git-ignored. `.env.example` lists variable names
  with placeholder values and is committed.
- Never paste a real `.env`, password, API key, or token into chat, issues, commits, or docs.
  If a secret leaks, rotate it immediately.
- Passwords are stored hashed. Device API keys are stored hashed.
- Firmware secrets (Wi-Fi password, API key) live in `secrets.h`, which is git-ignored, with a
  committed `secrets.example.h`.
- The LLM receives measured facts only. It never receives personal data, credentials, or
  images, and it never decides the plant class.
- Production runs with `FLASK_DEBUG=0`, a strong `SECRET_KEY`, and CORS limited to the known
  frontend origin.

## 11. Definition of done

A change is done when:

- [ ] It meets the requirement it was written for.
- [ ] Linters and formatters pass (`ruff`, ESLint, Prettier).
- [ ] Tests for new logic exist and pass; bug fixes include a regression test.
- [ ] User-facing text is Indonesian and comes from `locales/id.ts`.
- [ ] Database changes include a reviewed migration and an updated [Schema](Schema.md).
- [ ] API changes are reflected in [API](API.md).
- [ ] No secrets, large data files, or debug output are committed.
- [ ] The commit messages follow section 4.2.

## 12. Testing

| Level        | Tooling                                                                  | Scope                                                                          |
| ------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Backend unit | pytest                                                                   | Services: classifier, stabilizer, alert rules, advisor validation and fallback |
| Backend API  | pytest + Flask test client                                               | Auth, ingestion, validation errors, permissions                                |
| Vision       | pytest with fixed sample images                                          | Each preprocessing function on known inputs                                    |
| Frontend     | Component tests where logic exists; manual check of the four page states | Forms, tables, status badges                                                   |
| End to end   | `scripts/simulate_device.py` against a running stack                     | Sensor post to dashboard update                                                |

Tests never call the real LLM provider; the advisor is tested with a fake provider and with the
rule-based fallback.

## 13. Documentation

- A document has one purpose and links to related documents instead of repeating them.
- Update the relevant document in the same pull request as the change it describes.
- Architecture decisions that are hard to reverse are recorded as ADRs in `docs/adr/`
  (`NNNN-short-title.md`, numbered in order, never renumbered; superseded ADRs stay and are
  marked as superseded).
- Documents use tables and short lists for facts, prose for reasoning, and Mermaid for diagrams.
- Dates use `YYYY-MM-DD`.
